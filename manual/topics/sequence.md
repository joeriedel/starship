# Sequences

When the user asks for several steps, build a sequence: `ensign sequence run supernova/<task>`, `ensign sequence publish supernova/<task>`, `ensign sequence release supernova <version>`, `ensign sequence do <instruction>`. Give the sequence a short name saying what it is for with `--name` on its first step, for example `ensign sequence do <instruction> --name "hygiene fixes"`; later steps join it and take no name. Steps are numbered from 1 in each sequence and addressed as `<seq>.<step>`, for example `5.3`; a plain `<step>` works only while exactly one sequence is open. Show the listing it prints; one `go` approves it as shown and the steps then run one after another. Set `ensign sequence mode keep-going` only when the user asks for it; nothing else sets it. After each run write its journal account, and report each step as it finishes, leading each report to the user with that step's `Step X/Y`, the position shown in the go reply, the Stop message or command output when the step started; a publish's report carries its own `Step X/Y` and its outcome, and reaches you once, in the next Stop message or prompt; a cancelled publish has no position: never work a number out. A release step runs as a background command when the Stop hook names it. A `do` step is yours to carry out, then `ensign sequence done <seq>.<step>` or `fail <seq>.<step> --reason`; never edit a workspace for it (the edit guard still applies). Publish only as an approved publish step; any other push still needs the user's ask. A publish fails if a run of the task in that location failed after its last pass, even after accept or halt; run the task again first. In stop mode, when a run step fails, the sequence waits. Every failed attempt goes to the user, however many retries came before; you never retry on your own. Offer exactly retry, skip, halt, in that order, and wait for the answer; never say `accept` to the user. Your message to the user is a full brief every time, even if an earlier message said the same: what failed and why in plain words, the state of the work, what each of retry, skip and halt does, and every decision a retry needs with each option spelled out and a recommendation; never refer to an option by letter or by pointing at an earlier message, because the Stop hook repeats itself and earlier text scrolls away. Stop mode: retry is `ensign sequence retry <seq>.<step> --diagnosis "<why>" --state "<what is left>"` (fill both in after the user chooses retry); skip is `ensign sequence skip <seq>.<step>`, which ends the step as failed, cancels its task's publish step and lets the rest of the sequence run; halt is `ensign sequence accept <seq>.<step>`, which ends the step, halts the sequence and cancels every later step. Keep-going mode never asks: a failed run step ends at once, that task's later steps are skipped and the rest carries on; there is no decision and you never retry, skip or accept. When the sequence closes, one report, delivered once in the Stop message or the next prompt, lists the failed steps with why, the steps skipped or cancelled, and the state of the failed runs' folders; relay it to the user in plain words. Skip's output names the workspace state of the failed runs' folders (changed paths and branch, or that it is clean) and the later steps it may affect, in this sequence and in later ones: release steps, `do` steps naming the task, run steps of the task, and publish steps of the task in later sequences. A later sequence's publish of a skipped task is cancelled when reached, unless the task runs again and passes in that location first. Run steps of other tasks aren't flagged because each starts from master. A sequence that carried on past a skip closes as finished with a skipped step; a keep-going sequence closes as finished with its failed steps. Report every retry and write its diagnosis in the journal. In keep-going mode, if continuing is wasted, you may run `ensign sequence halt --reason <why>` and say why.

A retry's work item is the task's current Goal and Scope, and its subtask's, read from the bridge's working tree when `retry` is called (no commit needed); then the first run's project rules; then `--diagnosis` and `--state` as `## Current state`. To carry a changed brief to a retry, edit the task file before running `retry`. A task file left with neither Goal nor Scope refuses the retry. Steps that haven't started keep the work item from when they were added.

When a session has moved, `ensign sequence run|publish|do|release`, a plain `ensign run` and `ensign writes add` are refused and name the new session; do the work from that session. A sequence left behind on an earlier session is not carried over: tell the user to resume that session, which drives it or lets it be halted.

When several runs of the session are live:

- Pass `--run <id>` to `ensign next`, `ensign resume` and `ensign run-stage`; without it they refuse and name the live runs.
- One run per code folder: start a run or a step there only when no other live run of any session holds the folder. Ensign refuses it otherwise; a step left waiting starts once the folder is free.
- Each run finishes on its own: write each one's journal account as it ends.

When a run step names a task with subtasks:

- The step holds a group of runs, one per subtask, side by side; `go` and each later group's start return one dispatch instruction per run. Dispatch every lead, passing the prompt exactly as given: its first line names the run.
- The Stop hook names every lead still waiting to be dispatched.
- A failed run does not stop the others of its group. When all are over, in stop mode the step waits: `retry` reruns only the failed ones, `accept` ends the step and later groups do not run; `skip` likewise. In keep-going mode the step ends failed and later groups do not run.
- Details: `ensign help subtasks`.

When the project declares locations:

- A run step for a task with several locations needs `--location <name>`; `--sides <a,b>` narrows its sides. Both go on `ensign sequence run`.
- Retry keeps the run's location. It keeps the sides only if the old run was narrowed; otherwise the retry takes the default sides.
- A release step takes `--location <name>`: `ensign sequence release <project> <version> --location <name>`. Its `@release` is the project's overridden by that location's, and it runs in that location's folder. Without `--location` the project's only location is used; with several, the step is refused.

A run that could not be retired under a cancelled or skipped step stays pending and is retried at each advance and at session start; each failure and the retry's success are reported to you once, in the next prompt or Stop message.

A publish command runs under the session's sequence lock, so it can't call an `ensign` command that takes that lock (`sequence` commands, `run`, `go`): such a call fails at once.

A publish lands every location the preceding run step worked in, across all its subtask groups, dependencies first, and stops at the first failure; its report names what landed, what was never tried and what failed. After a failure, a new `ensign sequence publish supernova/<task>` lands only the locations left, and needs no run step before it.

Drop pending steps of an approved sequence with `ensign sequence drop <seq>.<step>... --reason <why>` only when the user asks; it keeps the rest running, and dropping a run step drops its task's publish step.

Before `go` the sequence is yours to rebuild: `ensign sequence drop <seq>.<step>...` removes steps (the rest renumber; publish rule as above), `ensign sequence discard` removes the whole sequence so the next step starts a fresh one. To reorder or insert a step (say a `supernova` publish step between two runs), drop the later steps and add them again in the new order. `halt` stops work that has begun; don't use it to rebuild. Halt leaves a run with a lead running; end it with `ensign run stop <run>`.

- `ensign sequence` shows the open sequences; `ensign sequence --all` shows every sequence in the session, finished ones included.
